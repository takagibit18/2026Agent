 ### 只读工具
 read_file使用offset/limit按行切片
 - offset：从第几行开始读（从 0 开始数）。offset=0 表示从文件第一行开始；offset=220 表示跳过前 220 行，从第 221 行开始读。
- limit：最多读多少行。比如 limit=30 就只返回 30 行（从 offset 起算的 30 行）。
好处:根据diff信息里的行号,快速把 token 花在“==改动附近==”,在大文件中占优势

在 review/debug 系统提示中加入明确策略:
- 路径不确定时先 list_dir，再 glob/grep/read_file
- 遇到 “Directory/File not found” 时必须先校验父目录，不允许盲目重试同路径。

在==工具反馈==折叠==摘要==中突出“失败工具调用 + 原因 + 推荐下一步”，==减少无效迭代==。

### LLM并发控制

#### asyncio事件循环（Event Loop）
asyncio≠多线程
asyncio是单线程,唯一一个主线程的作用就是**运行事件循环**,本质职责有三个:调度 + 分发 + 恢复执行
##### 主线程的工作:
1️⃣ 调度协程（谁先执行）
```
asyncio.create_task(coro)
```
主线程会：
- 把 coroutine 包装成 ==Task==(任务是事件循环的基本==调度单位==)
- 放进“就绪队列”（ready queue） **就绪队列内部是FIFO**
2️⃣ 执行协程（但只执行一小段）
```
await some_io()
```
主线程开始执行协程代码,一旦遇到await就立即停止当前协程,切换去执行别的协程
主线程不会执行完整个函数，而是==“切片执行”==
3️⃣ 监听 I/O 并恢复协程
主线程会监听运行情况,通过创建socket等待事件发生,哪个 ready 就==恢复==哪个==协程==

##### 三种调度方式

| API            | 调度方式         | 返回时机    | 顺序     | 典型用途                            |
| -------------- | ------------ | ------- | ------ | ------------------------------- |
| `gather`       | 一次性调度全部      | 全部完成    | 按输入顺序  | 并发调用多个 LLM(需要==顺序==稳定的==全部结果==) |
| `wait`         | 调度 + 可控制完成条件 | 可部分返回   | 无序（集合） | 多模型 fallback（谁快用谁）              |
| `as_completed` | 调度后逐个产出      | 谁先完成谁返回 | 完成顺序   | 工具并发 + 流式输出(耗时最短)               |

##### asyncio应用场景(IO密集任务)
1. 并发调用 LLM:发送多个prompt时,并发处理API请求,提高LLM吞吐量
2. 工具调用并发:只读工具可以==无副作用==的并发(读写工具并发可能会产生==竞态条件==(race condition)导致覆盖写)
3. streaming 输出（SSE）:并发推送数据

### 容器(项目)
#### 为什么要过滤传给容器的环境变量？
因为宿主机上的环境变量里可能包含敏感信息，比如：
- PATH
- 各种 token
- API_KEY
##### 如何实现过滤?
两层过滤:
第一层是宿主机侧的“清洗”,先从 parent_env 或 os.environ 取原始环境变量。
然后按照白名单 + 敏感前后缀过滤一遍:
- 保留白名单:PATH、HOME、USERPROFILE、LANG、LC_ALL、PYTHONPATH、VIRTUAL_ENV、SYSTEMROOT、TEMP、TMP
- 丢弃敏感前后缀:OPENAI_、AWS_、AZURE_、GITHUB_，后缀 _KEY、_SECRET、_TOKEN、_PASSWORD
第二层是容器侧的“再过滤”,把不适合容器继承的宿主机变量挡掉。
因为容器和宿主机的文件系统往往不一致,所以宿主机的PATH,HOME,TMP等路径可能会污染Linux容器中的默认路径. 只把适合容器消费的变量通过 -e 传进去即可.

#### 为什么容器化对 Agent / 工具执行场景有帮助？
Agent 经常需要执行代码、跑测试、操作文件。  
如果直接在主机执行，风险会比较大。  
容器化可以让每次执行都更隔离、更可控。

这样对于 Agent 来说：
- 更容易==复现==
- 更适合==自动化==执行
- 更==安全==
- 便于标准化测试

#### 在 Docker 中执行命令时，为什么要避免 shell？
因为直接用 shell 拼接命令，可能会带来安全问题,例如 ==shell 注入==、==命令拼接风险==。
解决方法:把==命令参数作为 argv== 直接传给 Docker，而不是拼成一整串 shell 字符串。
好处:
- 参数边界更清晰
- 更不容易被恶意输入利用
- 命令执行更可预测

  #### 挂载路径怎么来的？
  ###### 1）挂载路径怎么来的？
  挂载路径不是“自动猜出来的”,而是**宿主机路径 + 容器内目标路径**一起指定出来的。
  例如:
  ```bash
  docker run -v E:/project:/workspace ...
  ```
  这里左边 `E:/project` 是宿主机的真实目录,右边 `/workspace` 是容器里的挂载点。
  对 Agent 来说,这个路径通常来自三种地方:
  - 用户传入的项目根目录
  - 编排器当前工作目录(`cwd`)
  - 临时工作区 / 沙箱目录
  
  本质上就是:先确定**宿主机上哪一份数据要暴露给容器**,再决定**容器里挂到哪里**。
  容器内部只认右边这个路径,所以后续所有读写都要围绕这个挂载点来做。
  
  ###### 2）怎么保证安全和完整？
  ##### 安全
  - 只挂载**必要目录**,不要把整台机器随便暴露进去
  - 挂载前先做**路径校验**,防止 `..` 之类的路径穿越
  - 对敏感目录做白名单控制,避免把 token、密钥、系统目录带进去
  - 尽量用**只读挂载**给检查类任务,只在确实需要改文件时开放写权限
  
  ##### 完整
  - 挂载后先检查容器内是否能看到目标文件,避免“挂上了但没挂对”
  - 确认宿主机路径和容器路径一一对应,不要因为大小写、盘符、相对路径导致错位
  - 读写同一份项目时,保证所有后续工具都使用**同一个挂载根目录**
  - 如果容器里要生成新文件,要确认写回的是挂载目录而不是容器临时层
  
  ##### 一句话理解
  挂载路径的核心不是“路径字符串长什么样”,而是**宿主机文件系统和容器文件系统之间的映射关系**。
  只要这个映射稳定,Agent 才能稳定地读到输入、写回结果、复现执行过程。

### PDF解析
PDF 解析主流技术大致分几类：
1. **文本层抽取**
    - 代表：pypdf、pdfminer.six、pdfplumber、PyMuPDF
    - 适合：原生电子 PDF，文本可复制。
    - 优点：快、便宜、结构损失较小、不需要 OCR。
    - 缺点：遇到扫描件、图片 PDF、复杂字体编码、表格/多栏排版时容易丢内容或顺序错乱。
2. **版面感知解析**
    - 代表：pdfplumber、PyMuPDF block/word API、unstructured、LayoutParser
    - 适合：简历、合同、表格、多栏文档。
    - 优点：能保留段落、坐标、列、表格等布局信息。
    - 缺点：实现复杂，需要针对业务做排序、分栏、标题识别。
3. **OCR 解析**
    - 代表：Tesseract、PaddleOCR、EasyOCR、Google/Azure/AWS OCR
    - 适合：扫描 PDF、图片型 PDF、拍照件。
    - 优点：能处理没有文本层的文件。
    - 缺点：速度慢，对清晰度/语言包/版面敏感，容易错字、漏字、顺序错乱。
4. **视觉模型解析**
    - 代表：OpenAI vision、多模态 LLM、Document AI 类服务
    - 适合：复杂简历、混合图文、OCR 表现差的材料。
    - 优点：对布局和语义理解更强，可以直接抽结构化字段。
    - 缺点：成本高、依赖网络和 API，必须控制隐私、日志脱敏和可追溯性。
5. **混合流水线**
    - 常见生产方案：文本抽取优先，质量不够再 OCR，OCR 仍不够再 vision/Document AI。
    - 当前项目就是这个方向：pypdf(==**优先走文本抽取**==) -> PyMuPDF render(低质量 PDF使用 PyMuPDF 把 PDF 页面==渲染成图片==,渲染后的页面图片复用现有==图片解析链路==) -> Tesseract OCR(先走本地图片解析) -> vision fallback(如果OCR也为空,则降级为==vision model解析==兜底)。

### 如何评估PDF解析质量
1. **文本质量指标**
    - 有效字符数：是否低于阈值。
    - 空白比例：是否抽出大量空行。
    - 控制字符/乱码比例：是否出现大量不可见字符、�、异常编码。
    - 语言覆盖：中文/英文是否明显缺失。
    - 页数覆盖：多页 PDF 是否只抽到第一页或少量页面。
2. **结构质量指标**
    - 是否识别出关键章节：教育经历、工作经历、项目经历、技能、证书、语言。
    - 简历核心字段是否存在：学历、专业、学校、公司、岗位、时间、技能、证书。
    - 段落顺序是否合理，是否把左右栏、页眉页脚、表格内容打乱。
    - 是否重复大量内容，例如页眉页脚、联系方式反复出现。
3. **业务可用性指标**
    - hard gate 证据是否可追溯：学历、专业、证书、年限是否能在 CV 文本中找到原始证据。
    - candidate profile 是否足够密集：experiences/projects/skills/verified_evidence 是否为空或过短。
    - scoring 前质量门槛：如果 CV 文本过短、乱码高、关键章节缺失，应给 warning，避免把低质量解析结果当成真实低匹配。
    - 人工抽样对比：抽若干真实 PDF，比对“原文可见信息”和“系统抽取结果”，统计漏抽、错抽、乱序、伪证据。

### Agent项目安全隔离
最核心功能:**让 Agent 能“看”和“验证”，但不能随便==读仓库外文件==、不能随便==执行危险命令==、不能==在 Review 场景里执行命令==。**

**1. 工具按风险分级**
工具分为只读,执行,写入类,写在工具定义和注册表中,==编排层==可以根据工具风险决定==“能不能暴露给模型”“执行前要不要确认”==

**2. Review 和 Debug 能力隔离**
项目中的
- review：只做代码审查，==不暴露执行工具==
- debug：允许在受控条件下使用 run_command / run_tests
在编排层里的逻辑:Review 创建 registry 时 include_execute=False，Debug 才是 include_execute=True
为什么要这样做:**模型在 Review 模式下连执行工具的名字都看不到。** 这比“看到了但不让用”更安全。

**3. 路径被限制在 workspace 内**
只读工具和执行工具都不能随便访问系统路径。
- 编排层会把当前仓库路径绑定成 workspace_root
- 工具收到路径后，会解析成绝对路径
这层防的是：  
**Agent 通过文件工具==读取项目外的敏感文件==。**

**4. 命令执行有白名单和 shell 禁用**
在 src/security/exec_policy.py 里，命令会先经过：
- shlex.split 拆成 argv
- 检查第一个 token 是否在白名单里
- 禁止 &&、|、;、>、$() 等 shell 元语法
- git 只能用只读子命令，比如 status、diff、log
这样能防止执行危险组合

流程:
LLM 提出 run_tests
        ↓
编排层检查：这是 EXECUTE 工具，需要高危门控
        ↓
工具层检查 cwd 是否在 workspace 内
        ↓
exec_policy 检查命令白名单和危险 token
        ↓
sandbox 统一解析 workspace/cwd
        ↓
subprocess 或 docker 后端执行
        ↓
返回 SandboxResult

**这个项目的安全策略重点**  
它不是靠单点防护，而是多层拦截：
- 模式隔离：Review 看不到执行工具
- 工具分级：执行类工具需要特殊处理
- 路径隔离：文件和命令都限制在 workspace 内
- 命令隔离：白名单 + shell=False
- 环境隔离：清洗环境变量
- Docker 隔离：可选容器运行，默认无网络、低权限
- 结果结构化：失败也返回可审计信息

对初级 Agent 开发者来说，最值得学的是这个原则：

==**不要相信模型会“自觉安全”==。要把安全边界写在工具层、编排层和执行层里，让危险行为根本没有路径发生。**
